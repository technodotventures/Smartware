# A warranted CORRECT is durable: the retraction reaches the canonical log, and recall serves the corrected value — composed onto the Coffee RC (B1 of the GATE review t_66f1dd7d)

## Intent

Close blocking finding **B1** of the independent Coffee GATE review (`t_66f1dd7d`, verdict BLOCK): a
correction that a human warranted was not durable. Measured by the reviewer over two processes on the
installed `smartware-0.7.0.tgz`: recall answered `[]` immediately after `correctClaim`, and after a
restart it served **both** the corrected value and the corrected-away value as `status: 'active'`,
because the retracted claim canonicalised as `v1 active` + `v2 active` — the retraction never reached
`<brain>/claims/<month>.jsonl`, so every replay (restart, index rebuild, `restoreScope`,
export → import) resurrected the value a human had marked wrong.

The card asked for three things: compose the already-written fix onto the Coffee RC branch, add a gate
check that restarts the brain between CORRECT and recall (with a positive half for check 3f), and re-run
`npm run verify:coffee-gate`.

**Out of scope:** B2 (the `op_LEGACY…` operation-id / `semantic` key divergence, card `t_5ef44cc1`) and
B3 (grant-row shape, card `t_864a5900`); the ADR numbering arbitration (`t_201cdca8`) — this lane mints
no new ADR number and carries the one already reserved for it (`0016`); any repair pass over existing
pods' canonical logs.

  verb now re-syncs exactly as `consolidate()` already does (`src/core.ts`: `syncSearchFromClaims(store,

- **3f gains its positive half.** "Stops serving the wrong value" is satisfied by an empty result set, so
  the check now also requires the corrected value to be *served* (`servedCorrected.length === 1`). This
  is exactly why the gate missed B1: it asserted only the negative half.
- **3j–3o**, a dedicated drill on its own fact (`B1 Restart Probe Co` / `b1_probe_date`) so "which row
  answers" is unambiguous: baseline one row → CORRECT → recall serves the corrected value in-process (3k)
  → **restart as a new adapter instance over the same brain dir** (3l) → the canonical log's *latest*
  version of the retracted claim is not `active` and no claim whose latest version is `active` asserts the
  corrected-away value (3m) → **the same question from a genuinely separate process** (3n) → and the
  restarts append no canonical record at all (3o).
- **3n** is a real second process (`scripts/coffee-correction-restart-probe.mjs`, copied next to the
  installed package by `scripts/coffee-company-brain-gate.mjs`): it shares only the brain directory, brings
  its own host ports, and takes its fence epoch from the shared arbiter — as Redis would mint it. The
  fixture re-acquires a newer epoch afterwards, so neither side is ever the stale owner.
- **Honest reading of literal "no canonical version carries `state: 'active'`":** version 1 of a retracted
  claim *is* `active` — it was, when it was written, and the log is append-only and never rewritten. What
  the correction must fix (and did not) is the version a replay reads as current. 3m therefore asserts the
  latest-version rule plus the value-level consequence (no live canonical record asserts the retired
  value), and its detail prints the whole lineage so a reviewer can see v1 `active` / v2 `forgotten`.
