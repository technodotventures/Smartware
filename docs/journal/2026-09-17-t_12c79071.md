# The claim-FTS lane survey: REVIVE is the third verb of the class; FORGET, RETENTION, ENDORSE and QUARANTINE_REVIEW measured clean

## Intent

One pass, not one card per verb: **which `SmartwareCore` verbs move claim rows through the store
(`syncFromJsonlVersion` / `insertClaim` / `updateClaimStatus`) without re-syncing the claim-FTS lane,
so that the live process and every restart disagree about what recall serves?** The class had been
measured twice — CORRECT (`t_8ddfa350`, PR #25) and REVISE (`t_336ba0b9`, PR #29, whose card carried
this survey explicitly rather than one card per verb). The invariant asserted for every lead:
**after any claim-row mutation, in-process recall == what a fresh open of the same brain serves**.

The card's four leads were code-read only, to be reproduced before anything was touched: `forget.ts`
(`handleForget` / `handleRevive`), `retention.ts` (`handleExpireRetention`), `endorse.ts`,
`quarantine_review.ts`. Out of scope and named as such: the demotion carry-forward decision
(`t_01ef0ede` / `t_742e31f9`, unmerged), the pre-ADR-0016 canonical-log repair (`t_a54a4606`), the
verified wrappers (`forgetScope`, BYO), and any re-litigation of FORGET's deliberate keep-rows design
(`src/protocol/forget_scope.ts:518-527`) — the survey was to respect it, not settle it.

Base check first, as the card asked: `wip/neo/demotion-durability` @ `e5f093e` is contained only in
`wip/smarty/demotion-handbuilt-records` @ `3ae8a6b` and is in neither `origin/fix/b1-correction-durability`
nor `main`, so it is not a merge target yet — this lane is based on `fix/b1-correction-durability`
@ `ab9cf2b`, the base the two sibling fixes use.

## What was measured

Instrument: `scripts/mutation-restart-probe.mjs` (this lane), three legs — mutate through the open
brain, recall **in-process**; open a **new core instance** over the same brain directory and recall;
ask the same question from a **genuinely separate process** (only the brain directory is shared).
Stated deviation from the `t_336ba0b9` instrument: that one drove its mutation and reads through the
Coffee reference adapter, and the adapter exposes no FORGET/REVIVE surface (`correctClaim` only), so
this variant drives `SmartwareCore` directly — the surface the survey is about — while keeping the
three-leg structure, the report shape and the exit-code contract
(`scripts/coffee-revise-restart-probe.mjs` remains the adapter-driven precedent). The in-repo pin
uses the `t_336ba0b9` pattern: `test/protocol/claim-mutation-search-sync.test.ts`, in-process vs
fresh open, one measurement per lead, with the intervening write being CONSOLIDATE (on this base
REVISE does not yet re-sync — PR #29 is unmerged — while `consolidate` re-syncs unconditionally).

### RED — lead 1 has exactly the class, on **both** forget target shapes

At the lane base `ab9cf2b`, sequence *forget → later write in the scope → revive*:

- **claim-target FORGET** (`--scenario forget-revive`): leg 1 (in-process) served **0 rows**; leg 2
  (restart) and leg 3 (second process) both served the revived claim. Canonical history
  `[(1, active), (2, forgotten), (3, active)]`, derived row `active`, scope `client:acme#1`.
- **observation-target FORGET** (`--scenario forget-observation-revive`, the claim's sole evidence):
  same shape — leg 1 **0 rows**, legs 2 and 3 the revived claim; canonical
  `[(1, active), (2, active), (3, forgotten), (4, active)]`.

Mechanism, shared with the two earlier instances of the class: FORGET keeps the claim-FTS row on
purpose and every read path filters forgotten claims at query time, so *what recall serves* is equal
right after the forget (`total_found 1 / filtered_out 1` in-process vs `0 / 0` after a rebuild —
measurement 1 below). But **any later re-syncing write in the scope** (correct, revise, consolidate,
restoreScope, compile/reflect) replaces the scope's lane with the store's indexable set, which no
longer contains the forgotten claim — the deliberately kept row is gone. REVIVE then appended the
active version through `store.syncFromJsonlVersion` and touched no index, so the re-admitted claim was
in the canonical log, in the derived row and in every restart's answer, and absent from the live
process's answer until some further write happened to re-sync the scope. A user action that restores
a fact the durable surface serves, and that the live brain answers with nothing, is the same
data-loss-shaped divergence as CORRECT and REVISE.

### Measured negatives (the mechanism is asserted, not assumed)

- **FORGET alone** (measurement 1): served ids identical in both views (`[]`); the kept row shows up
  **only in the counters** — in-process `total_found 1 / filtered_out 1` vs fresh `0 / 0`. By design,
  and left alone.
- **retention expiry alone** (measurement 3): identical ids (`[]`) and the same counter-only
  difference (`1 / 1` vs `0 / 0`). The **raw observation window** is also rebuild-equivalent *without*
  any reconcile, for a different reason than the claim lane: `searchObservations` re-checks Layer 0's
  effective status per hit (`src/core.ts:1069-1088`), so the tombstoned observation is dropped live
  even though its index row still says `accepted` (both views `[]`).
- **retention expiry + later write + REVIVE** (measurement 4): all three legs agree and **none** of
  them serves the re-admitted claim (`durable_surface_serves_revived_claim: false`), while the
  canonical record is `active` and the derived row says `active`. That is not this class: it is the
  evidence lifecycle — `isEffectiveCurrent` keeps a claim out of every read interface while none of
  its source observations is `accepted` (`src/layer1/effective_current.ts:36-55`). For an
  evidence-tombstone retraction, REVIVE restores the **record**, not retrievability, and it does so
  consistently in every view. Worth stating plainly because it is the honest limit of the fix below.
- **ENDORSE** (measurement 5): identical views (one row, `1 / 0` both sides). Endorsement appends an
  **ACTIVE** version and changes `author` / `epistemic_owner` only; the lane's row content is
  subject/predicate/object (`syncSearchFromClaims`), so the indexable set is unchanged.
- **QUARANTINE_REVIEW approve** (measurement 6): the claim rows are byte-identical before and after
  (an `id:status` list compared), and both views are identical. The verb is observation-level; the
  parent is skipped by replay's watermark, so no claim row moves and the lane needs no re-sync.

## What was done

`src/core.ts`, `revive()`: after `handleRevive`, the revived claim's scope is re-synced — REVIVE
writes the claim row through `store.syncFromJsonlVersion` and the claim-FTS lane is rebuilt only by
`syncSearchFromClaims`, which nothing called — via
`syncSearchFromClaims(this.store, this.searchIndex, <scope from the store>)`. Same layer and shape as
the CORRECT and REVISE fixes; the scope is read from the store so `ReviveResult`'s shape is untouched.

The re-sync is **semantics-neutral** (it makes the lane equal to whatever the store says is
indexable), so it holds under either demotion reading — the question the unmerged lanes own.
FORGET's keep-rows design is **not** touched. One consequence is worth recording: the design comment
that justifies the keep ("a revived claim becomes searchable again without waiting for a reindex")
is now carried by REVIVE's own re-sync rather than by the kept row, so the guarantee survives an
intervening write — which is precisely the case that was broken.

Regression pin: `test/protocol/claim-mutation-search-sync.test.ts` — six measurements, one per lead,
each pinning the invariant and, for the negatives, the mechanism that keeps them clean.

  the class (after CORRECT and REVISE) and is fixed where the other two were fixed. FORGET (both
  target shapes), retention expiry, ENDORSE and QUARANTINE_REVIEW are measured clean for what recall

## Unresolved

- **The counter divergence is measured and deliberately not fixed.** Live `total_found` /
  `filtered_out` differ from a rebuild by the lanes' kept rows (measurements 1 and 3). It is the
  documented keep (FORGET) and the sweep's mirror of it (retention), and it stays inside the
  snapshot filter, so no served row is wrong. The settle question is now genuinely open rather than
  settled by history: the kept row no longer carries REVIVE's guarantee, so dropping rows at FORGET
  would make the two views equal *exactly*, at the cost of the design's stated rationale. Routed to
  the orchestrator on the board, not decided here.
- **Unprobed static lead (code read only — reproduce before touching).** The async compile worker
  mirrors new versions into the lane incrementally (`indexSingleClaims`: DELETE+INSERT per handed-over
  claim, `src/compile_queue/worker.ts:212-217`) instead of replacing the scope, so rows for claims it
  did not hand over stay behind — e.g. a claim demoted by `admitClaim` inside replay
  (`src/layer1/replay.ts:194` → `src/layer1/conflicts.ts:123`). Served recall should stay
  rebuild-equivalent by the same snapshot filter; the counters would not. Not measured here.
- **Not proven:** independent verification of this lane (the evidence is producer-run; the RED/GREEN
  pair is recomputable in a detached worktree, which is stated in the evidence README).
- **Not measured against the demotion lanes** (`t_01ef0ede` @ `e5f093e`, `t_742e31f9` @ `3ae8a6b`,
  both unmerged and not on this base). The fix was written to hold under either carry-forward
  semantics; that is an argument, not a measurement.
