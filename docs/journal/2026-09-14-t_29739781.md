# smartware docs+SDK: saas-integration recipe teaches the silent duplicate-claim pick

## Intent

Follow-up from host pilot `t_ec159c21` (brain-pilot, Coffee-shaped Redis + Smartware 0.7.0). The pilot's write path had a duplicate-claim defect; the fix is landed and verified host-side. **The library's own integration recipe contains the same defect**, so the next host that follows the docs reproduces it.
## The finding (VERIFIED)
`node_modules/smartware/docs/integration/saas-integration.md:202-203` (installed 0.7.0 tarball `d0cc5bfc`; source in `<checkout>/smartware`) documents:
const existing = store.getClaimsBySubject(subjectId, 'active')
.find(c => c.predicate === predicate && c.scope === scope && ...)
Two problems with that recipe, both measured in the pilot:
1. `ClaimStore.getClaimsBySubject` has **no ORDER BY**. When a store already holds two active claims for one fact, `.find()` returns whichever row SQLite yields first — the survivor becomes row-order dependent, and nothing in the result says a choice was made.
2. The neighbouring note about `canonicalKey` is worth stating explicitly: it keys on `validity_from`, which a host that stamps `now()` on every write can never match — so hosts must match the fact itself, not the canonical key.
## The contract the pilot implemented (decided; document this, do not re-litigate it)
- Collect **every** active match for (subject, predicate, scope, object value, `validity.to === null`), not the first.
- Survivor = **lexicographically smallest claim id**. Claim ids are ULIDs (time-ordered) ⇒ "earliest minted wins", independent of store row order.
- **Union** the losers' `supporting_evidence` into the survivor *before* demoting (a duplicate is the same fact observed again — dropping it loses provenance).
- Demote, never delete: `status='superseded'`, `superseded_by=<survivor>`, then recompute `confidence` with
