# The kept rows stay (decided, documented); the drain's mirror is not the divergence — and the demotion it needs is not durable on this base

## Intent

The settle + probe pass for two things `t_12c79071` (the claim-FTS lane survey, PR #33) measured or
noticed and deliberately left open:

1. the kept rows make the live counters diverge from a rebuild (measured there, now unmoored since
   PR #33 made REVIVE re-sync its scope) — an owner call between leave / drop the rows / redefine
   the counters;
2. a static lead: the async compile worker mirrors a batch's claims through `indexSingleClaims`
   (DELETE+INSERT per handed-over claim) instead of replacing the scope, so rows for claims it did
   not hand over stay behind — prediction: served recall stays rebuild-equivalent (the snapshot
   filters superseded), the counters do not; reached through `core.drainCompileQueue`.

The survey was not re-run. The base check was repeated first: the demotion lanes are still unmerged
(`wip/neo/demotion-durability` @ `e5f093e` is contained only in
`wip/smarty/demotion-handbuilt-records` @ `3ae8a6b`).

## 1. DECIDED: keep the rows; state the difference where integrators read

Instrument: `scripts/kept-rows-settle-probe.mjs` arm 1 on this lane's branch (tip `8f2f362`) — the
survey's measurement 1 re-confirmed as the settle artifact. FORGET (claim target): served ids
identical (`[]` in-process and after a fresh open); counters `total_found 1 / filtered_out 1`
in-process vs `0 / 0` fresh; after the fresh open's rebuild the in-process view is `0/0` too, so the
divergence is exactly the kept row and nothing else.

Decision — option (a), keep the rows:

- The keep is the documented, deliberate design (offboarding/erasure in `forget_scope.ts`; the claim
  target and the retention sweep mirror it). Nothing served is wrong: every read path filters
  forgotten/retracted claims through the authorized snapshot, so the served result set is
  rebuild-equivalent by construction.
- Option (b) — drop rows at FORGET/retention — would make the counters equal by making the lane
  writes heavier on two hot paths, and buys no correctness: the difference is exactly the kept rows,
  it cannot leak a served row, and the "kept row" story would have to be re-argued in the design
  docs for zero user-visible gain. Rejected.
- Option (c) — redefine the counters so they match a rebuild — would *hide* the lane's real state.
  The counters are honest raw-lane information (a hit existed; the eligibility filter dropped it);
  redefining them is a contract change on a returned field with no defect behind it. Rejected.
- What the decision did require is what was false: the design comment claimed "rebuild equivalence
  is maintained by the same snapshot filter, not by row presence" — true for served results, false
  for the counters. Fixed where integrators read: `src/protocol/forget_scope.ts:519-537` (the
  comment now states the measured shape, the exact size of the difference, that it is deliberate,
  and that REVIVE's re-admission guarantee is carried by `core.revive`'s re-sync, `t_12c79071`, not
  by the keep), `src/core.ts` revive() (references the corrected rationale),
  `src/protocol/recall.ts` (documents `total_found`/`filtered_out` as raw lane hits taken before the
  eligibility filters), `docs/retrieval.md` (same, where integrators read prose).

Comment/doc-only: no behavior change, no schema, spec, protocol or OpType change.

## 2. PROBED: the drain's incremental mirror — the lead measured out into two different things

Arm 2 (the card's sequence, on this branch): OBSERVE → `core.drainCompileQueue()` (worker mirror,
`worker.ts:212-217`) → append a `claim_extracted` event (later window, same key — the replay path
`replay.ts:194 → conflicts.ts:123`) → a catch-up verb (FORGET on a decoy; its `replayCatchUp` at
`forget.ts:383` is unconditional) → a second drain batch → `core.compile` (the re-syncing write
path) → fresh open. Store rows, lane rows, canonical records and the watermark are dumped at every
step in the report.

What the measurements say:

- **The drain is not the divergence (measured-negative).** The mirror is faithful for every claim
  the batch hands over (row content == the store claim it was built from), and rows for claims it
  did not hand over stay behind — by design, unchanged by a further drain batch (measured: a second
  batch leaves the stale C1 row and the missing C2 row exactly as they were). The repair is the
  re-syncing write (`core.compile` → `syncSearchFromClaims`), after which the lane equals it.
- **The card's predicted shape holds once the demotion is durable.** On the demotion lanes' tip
  (`3ae8a6b`, cross-check run): served ids equal in-process vs fresh for the demoted claim (both
  `[]`), counters differ by exactly the kept row (`+1`) — item 1's shape, confirmed.
- **On this card's base the prediction is falsified, and not by the lane.** On `8f2f362`: the live
  lane keeps C1's row (stale) and never indexes the admitted C2; live recall serves `[]` while the
  fresh open serves `[C1, C2]` — C1 *active again*. Mechanism isolated by arm 3:
  `applyTemporalSupersession → updateClaimStatus` calls `store.insertClaim`, which projects
  `state = statusToState('superseded') = 'active'` and (on this base) writes no superseding
  pointer, so the demotion's own canonical record says active; the next `SmartwareCore.open`
  re-materialises the store from the canonical surface (`ClaimStore.setDataDir`) and the demotion
  is erased — the resurrection happens at the open, before any recall. Measured in isolation: old
  record `state: active`, no pointer, `demotion_survives_rematerialisation: false`; on `e5f093e`
  and `3ae8a6b` the record carries `superseded_by` and the demotion survives (`true`). This is the
  demotion-durability defect's path (`t_01ef0ede`/`t_742e31f9`), reached through the replay
  admission entry point; it is not fixed on this base because those lanes are unmerged — the
  card's base-check note was the warning, and the probe now measures what it warned about.
- **A second, independent gap (served, not counters).** The catch-up itself materialises claims
  without re-syncing the lane: after it, live recall misses C2 until some re-syncing write runs.
  Reproduced on both bases (so the demotion lanes do not cover it). Same class as the survey's
  CORRECT/REVISE/REVIVE (a claim-row mutation without a lane re-sync); the mutator here is
  `replayCatchUp` inside `forget`/retention/quarantineReview. Routed as **`t_a6bf30a8`** (tech-head)
  with the sequence, the reachability caveats (needs a claim-materialising event this process has
  not replayed: a legacy/host `claim_extracted`, a `correction` from another writer) and a
  suggested fix shape.
- The resurrection path was reported to the demotion lane's independent verification record
  (comment on `t_30732060`): that audit enumerated the hand-built-record flows but did not exercise
  the `updateClaimStatus`/replay-admission entry; the cross-check above shows their fix covers it.
