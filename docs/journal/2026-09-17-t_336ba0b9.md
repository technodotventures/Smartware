# REVISE re-syncs the claim-FTS index: the process that performed a warranted revision serves what every restart serves

## Intent

The sibling card `t_8ddfa350` fixed the CORRECT half of this defect: a verb that appends claim
versions through the store without re-syncing the claim-FTS lane answers a warranted user action
with a claim the search surface cannot see (measured through the Coffee adapter; fixed by
`syncSearchFromClaims` after `handleCorrect`, exactly as `consolidate()` had always done). This
card probed the **same class for the newer REVISE verb** — code-read lead only, to be reproduced
before anything was touched — with the same instrument: write → REVISE → recall in-process, then
restart as a new adapter instance and as a genuine second process. Acceptance: a measured
RED/GREEN pair, a fix at the layer the evidence points to, a gate check **only if** the fixture
had a REVISE surface (it has none — the Coffee adapter exposes `correctClaim` only), and if the
probe came back clean, the negative result was to be the deliverable. It did not come back clean.

## What was measured (RED first)

Instrument: `scripts/coffee-revise-restart-probe.mjs` (this lane). Sequence: write a fact through
the Coffee reference adapter → a later event-valid window supersedes it → `core.revise({ target:
<the superseded claim>, set_confidence: 'high' })` through the open brain → recall **in this
process** → stop the owner, bring up a new adapter instance over the same brain directory →
recall → the same question from a genuine second process (own host ports; the fence epoch minted
by the shared arbiter, as Redis would).

At the lane base (`ab9cf2b`, pre-fix), RED:

- in-process recall right after the REVISE: **1 row** — the superseding value only (`2031-02-02`).
- a restart over the same brain: **2 rows** — the revised claim answers again
  (`2031-01-01`) beside the superseding value.
- the second process: 2 rows, same as the restart. Probe checks 4 and 5 fail; check 6 passes
  (the restart legs append no canonical claim record, so this is not a write divergence).

Mechanism: the claim-FTS lane (`claim_search_index`) is rebuilt from the derived rows by
`syncSearchFromClaims`. The superseding *write* re-synced its scope, which is how the superseded
claim left the lane. `SmartwareCore.revise` then appended version 3 through
`store.syncFromJsonlVersion` — the derived row moved (on this base the status flips back to
`active`) — and touched no index, so the live process kept answering from a lane that no longer
contained the claim, until some later write happened to re-sync the scope. Every restart
re-derives the derived rows from the canonical surface and re-syncs the lane
(`SmartwareCore.open`), so it answered with the claim: **same brain, two answers**, and a
warranted user revision that answers *nothing* is indistinguishable from data loss.

RED in-repo: `test/protocol/revise-search-sync.test.ts` run at `ab9cf2b` with the final test
content — 1 failed | 1 passed (failure: the fresh-open view `[original, replacement]` vs the
in-process view `[replacement]`). The control case (adjudicating an ACTIVE claim) passes at the
parent too, which is what makes the failing one a defect and not a setup artifact.

## What was done

`src/core.ts`: `revise()` now calls
`syncSearchFromClaims(this.store, this.searchIndex, <the revised claim's scope>)` after
`handleReviseSpec`, mirroring `correct()` and `consolidate()`. The scope is read from the store,
so the published `ReviseResult` shape does not move.

The re-sync is deliberately **semantics-neutral**: it makes the live lane equal to whatever the
store says is indexable, rather than asserting a direction. On this base a REVISE of a superseded
claim flips the derived status back to `active` and the durable surface serves both rows — the
fix makes the live process agree. The per-flow preserve-or-release question is **not re-opened
here**: it is the demotion lanes' decision (`t_01ef0ede` done at `e5f093e`; `t_742e31f9` decided
PRESERVE at `3ae8a6b`; both unmerged). This fix holds under either semantics because the sync
rebuilds from the store.

GREEN: the probe is 6/6 (in-process == restart == second process, 2 rows each); the test is 2/2;
the active-claim control still serves the claim with `confidence: 0.9` after the user's warrant.

## Where the regression pin lives

The fixture has no REVISE surface — the Coffee adapter exposes `correctClaim` only — so, per the
card's own conditional, no fixture check was added. The pin is
`test/protocol/revise-search-sync.test.ts`, which runs in `npm test`/CI and was RED-proven at the
parent commit. The three-leg probe remains the executable end-to-end instrument (it takes no npm
script, like `coffee-correction-restart-probe.mjs`).

## What this does not prove / boundaries (stated, not hidden)

- **Not** the semantics of a REVISE on a superseded claim (whether the target returns to default
  recall). That decision belongs to the demotion lanes (`t_01ef0ede` / `t_742e31f9`, unmerged on
  this base); this fix keeps the two views agreeing under either outcome and was written to stay
  correct when that lane composes.
- **Not** a survey of the other core verbs that mutate claim rows without re-syncing. The card
  places that in a single later pass rather than one card per verb; the reachable leads (endorse,
  retention expiry, forget/revive/forgetScope wrappers) are unprobed here.
- **Not** a repair for canonical logs already written by an older build (the B1-residual family,
  card `t_a54a4606`).
- Observed while probing, reproduced against this lane's fixed dist, and **not touched here**:
  temporal supersession is projection-only on this base — a superseded claim resurrects on a
  restart with **no REVISE anywhere** (`logs/v1-supersession-boundary.log`: in-process
  `status: superseded` / restart `status: active`, both served). That is the same gap the
  demotion-durability lanes own (their canonical `superseded_by` carrier covers the path); it is
  recorded here so the next reader does not mistake it for this lane's regression.
