# Smartware defect: a demoted duplicate is not demoted in canonical state — status 'superseded' is projection-only (compile-sync and rebuild restore it to active)

## Intent

## Defect
`resolveFactMatches` demotes a duplicate by writing **only the derived SQLite row**: `status: 'superseded'` + `superseded_by` (`src/layer1/store.ts:835` `updateClaimStatus` → `insertClaim`). The canonical L1 version record carries **no `status` and no `superseded_by` field at all**, and `statusToState('superseded') === 'active'` (`src/layer1/types.ts:126`), so the appended canonical version says `state: 'active'`. Two measured consequences, both reproducing, both violating what the repo says about derived state:
1. **A compile-path row sync re-activates the demoted duplicate.** `store.syncFromJsonlVersionsBatch` re-materialises the row from the canonical record and derives `status` from `state` (`src/layer1/store.ts` `claimVersionVals`, `status = v.state === 'active' ? 'active' : 'retracted'`). In the real flow this happens through the public API: after a §1e sweep converged recall to 1, one more autonomous restatement (which itself creates no new claim) put the same row back in the recall-eligible set and **recall answered twice again for one fact**. Row left inconsistent in the meantime: `status='active'` with `superseded_by='claim_0001…'` still set.
2. **A canonical replay loses the demotion entirely.** Replaying the L1 JSONL into a fresh projection gives both rows `status='active'`, `superseded_by=null`. The string `superseded` does not appear anywhere in the L1 JSONL.
## Why it is a defect, not a preference
- The repo's stated contract is that canonical state is primary and every view over it is regenerable (`AGENTS.md`; `src/core.ts:353-356` "wipe-and-rebuild equals the live index (rebuild-equivalence contract)"). A demotion that exists only in the projection is not rebuild-equivalent: a rebuild resurrects a duplicate.
