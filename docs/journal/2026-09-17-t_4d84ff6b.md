# A populated `notices` array now round-trips the page YAML serialiser

## Intent

Carded out of the round-1 review of `t_8d6f4a5c` (ADR-0013 → D2). That journal disclosed the
array-of-objects branch of the hand-rolled frontmatter serialiser as *untested*; the reviewer measured
that it is **broken**. `page-frontmatter.schema.json` (v0.5.0) and spec §9 declare `notices` as an array
of objects (`{type, message, claim_id?, tombstone_id?, posted_at?}`) — the slot a *user-authored* page
carries its staleness / contradiction / guardian notice in — and the writer emitted it as

```
notices:
  -     type: staleness
      message: reviewer probe notice
      posted_at: "2026-09-10T00:00:00.000Z"
```

(the item's own indent left inside the dash line, continuation lines at a *shallower* column), while the
parser's array branch read every `-`-prefixed line as a **string**. So
`parseFrontmatter(serialiseFrontmatter(fm))` returned `notices: ["type: staleness"]` and promoted the
item's remaining keys to stray top-level frontmatter keys, which the frozen contract rejects
(`additionalProperties: false`). Reviewer measurement at `5a1c58c`: 5/7 probe checks
(`attachments/t_8d6f4a5c/review-notices-tags-probe.out`).

**Out of scope, deliberately:** `schemas/v0.5.0/*.schema.json` and `SHA256SUMS` (no published byte may
move); the other lossy shapes of the same minimal serialiser (measured below and carded, not fixed here);
ADR-0013's decision and `Status` (owner merge gate untouched).

## What was done

Branch `fix/tech-head/notices-frontmatter-roundtrip`, stacked on the still-unmerged
`wip/tech-head/l2-page-frontmatter-schema @ 5a1c58c` (PR #22; the file this defect lives in is that
lane's, so the fix rides on it rather than on the ADR-0013 lane).

**1. The writer emits standard block YAML** (`src/layer2/frontmatter.ts` `toYAML`). The array-of-objects
branch now strips the item's own indent from the dash line and lets the item's remaining lines follow at
the item's content column:

```
notices:
  - type: staleness
    message: reviewer probe notice
```

The old bytes were not merely unparsable by *this* parser — no real YAML reader accepts a mapping item
whose continuation lines sit left of its first key. The page file is a git-versioned, user-facing
artifact (§9 voice protection), so the emitted bytes have to be standard.

**2. The reader decodes mapping items** (`parseYAML` → new `parseBlockArray`). An item whose content
opens a mapping (`key:` followed by whitespace or end-of-line) is decoded as an **object**, together with
its continuation lines — every line indented deeper than the item's dash. `parseYAML` is
indentation-agnostic (one `key: value` per line), so the item's block is handed to it whole.

- **Both sides, not half of each.** Writer-only is not a fix: emitting standard YAML leaves the parser
  still consuming the item line as a scalar. Parser-only would leave the page file non-standard. They are
  one format decision, so they moved together.
- **Plain items stay strings** (`- alpha`), and a scalar item whose content merely *looks* colonish is
  not mistaken for a mapping: `isMappingItem` requires the colon to be followed by whitespace, so
  `- http://example.com` stays a string.
- **The pre-fix bytes are read, not dropped.** A page written by the broken writer (a hand-authored user
  page that went through one compile/endorse before this fix) decodes from its mis-indented shape to the
  same object on the next read, so the corruption does not have to be recovered by hand. Nothing on disk
  is rewritten non-deterministically: the shape converges on the page's next write.
- A construct this parser has never read (a block scalar item, a nested sequence) is left where it is
  rather than silently swallowed; the measured cost of that is in *Unresolved*.

**Tests.** New `test/layer2/l2-notices-frontmatter-roundtrip.test.ts` (6): the unit round-trip
(`parse(serialise(fm))` deep-equal including two notices, no stray keys, serialise → parse → serialise
byte-stable); the emitted block pinned as an exact literal plus the "no `- ` + padding" signature; a
hand-authored page in canonical YAML read (scalar block items still strings, contract satisfied); the
pre-fix bytes recovered with no stray keys; the contract accepting the round-tripped page and rejecting
the measured pre-fix parse result on its stray keys; and the end-to-end carry-forward — compile →
ENDORSE → a notice attached to the user's own page → **recompile**, asserting the notice survives, no
stray keys, empty Ajv error list. The pin is **not tautological**: all six fail on `5a1c58c`.

## Resulting state

- `src/layer2/frontmatter.ts`: one writer branch and one reader branch agree on the `notices` shape in
  both directions, and the reader recovers the bytes the old writer left on disk. `schemas/` and
  `SHA256SUMS` are untouched (`verify:schemas`: 31 files OK).
- The deliverable is a reviewable branch; the push, the PR number and the CI matrix are read from the PR
  itself (`gh pr view <n> --json headRefOid,state` + `gh api repos/<o>/<r>/commits/<sha>/check-runs`) —
  a revision named in a journal goes stale on the next commit, so the PR is the pointer.
- `docs/conformance-status.md` gains the verified-baseline entry for this change, which **supersedes the
  entry below on one clause**: that entry states a user page's `notices` is preserved "verbatim" through
  a rewrite. The frontmatter *field* was carried by both writers, but the serialiser corrupted it on the
  way to disk, so until this change a user page carrying a populated notice lost it (and gained stray
  top-level keys) on its next compile or endorsement.
- The `t_8d6f4a5c` journal's migration paragraph made the same over-claim and is **corrected in place**
  in this commit. Journal files are write-once and hand-authored (`scripts/substrate-journal-sync.mjs`
  skips any task whose file exists), so a sync will not fix it and a later reader should not wait for one.
- `docs/STATUS.md` regenerated in a follow-up commit (the generator reads HEAD, so it has to be its own
  commit); it is not a CI gate.

## Unresolved

- **The serialiser's remaining lossy shapes** (measured above): a multi-line string anywhere (top-level
  `summary`, or a notice `message` — the value is dropped), a nested object inside a notice item (its keys
  are flattened into the item), and a single inline-array element containing a comma. All four predate
  this change, all are latent (no in-tree verb writes one today), and none is in this card's scope;
  carded as `t_cf744a8e` (DECIDE: support vs guard per shape) rather than fixed here.
- **No verb writes a populated `notices` array yet**, so this fix's live surface is the hand-authored user
  page (the §9 notice slot) and the writers that carry it forward: COMPILE's user-page branch and
  ENDORSE's cascade. The end-to-end test drives exactly that path.
- The page `scope` value is still the substrate's raw string — the ADR-0015 boundary, unchanged by this
  card.
