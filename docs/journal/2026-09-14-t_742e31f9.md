That fix records a mechanical demotion (`resolveFactMatches`) in the demoted claim's own **canonical version records** (`superseded_by` + `superseded_at`, stamped by `insertClaim` and carried forward on subsequent `insertClaim`-driven writes), and every materialisation derives `status` / `superseded_by` / `t_invalidated` from the record — so a compile-path sync and a canonical replay both keep the duplicate demoted.
**Boundary deliberately left in place** (documented in `docs/conformance-status.md` → *Remaining limits*, and integration guide §10): flows that **hand-build** a claim's next version record do not carry the pointer forward. Touching a demoted claim through one of them silently releases the demotion — consistently in live and replayed state (both derive from the same new record), but silently:
- `src/protocol/revise.ts` — the user REVISE record literal (~line 269). A user revising a demoted claim currently resurrects it into the recall-eligible set (a second copy of the fact) with no report.
- `src/protocol/forget.ts` — the forgotten version (~line 298) and the revived version (~line 574). Spec §11 says forgotten versions carry forward all non-content metadata and revival restores from the snapshot; the pointer is neither carried nor explicitly dropped.
- `src/protocol/endorse.ts`, `src/protocol/consolidate.ts`, `src/protocol/forget_scope.ts`, `src/protocol/retention.ts`, `src/protocol/reflect.ts` — assorted record literals; check which can touch a superseded claim.
