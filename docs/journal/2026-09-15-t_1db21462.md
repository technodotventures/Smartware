# DECIDE: a user-only way to re-pick which duplicate survives (release a mechanical demotion) — protocol surface + owner sign-off

## Intent

## Why this exists
`t_742e31f9` decided that a **mechanical demotion** (a claim demoted as a duplicate of a survivor by `resolveFactMatches`, §1e) is preserved by **every** flow — user `REVISE`, `FORGET`, `REVIVE`, endorsement, consolidation, offboarding, retention expiry. Rationale: beta has no verb that changes the fact a claim asserts (spec §6 — content is never rewritten in place), so releasing a demotion cannot add information; it can only add a second recall-eligible copy of one fact, which the next §1e write would re-demote. See `docs/adr/0003-claim-fact-identity.md` → *Carry-forward across hand-built version records*.
That decision leaves a real gap, recorded as a limit in three places (`docs/conformance-status.md` → *Remaining limits*, integration guide §10, ADR-0003):
**Beta has no way to release a mechanical demotion, and `invalidate_relations` cannot release one** — it withdraws an *admitted* `supersedes`/`corrects` edge, and the mechanical demotion is deliberately not an edge (no `relation_id` exists to withdraw). Consequences today:
- a user who believes the *duplicate* is the claim that should surface has no path;
- if the survivor is itself later forgotten, the fact leaves default recall entirely (the duplicate stays demoted, audit-visible only).
## The recommended shape (design opinion, not a decision)
Not "un-supersede the loser" — the next §1e write touching that fact would re-demote it (survivor = earliest-minted ULID is unchanged). The useful vocabulary is a **user-only "re-pick the survivor"** act that demotes the other copy, recording `origin: user` warrant. Open questions to settle before any spec text:
