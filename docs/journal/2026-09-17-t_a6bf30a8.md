# The catch-up re-syncs the claim-FTS lane: `replayCatchUp` reports the scopes it materialised, and every call site that owns a lane repairs them

mid-session `replayCatchUp` materialises claim rows without re-syncing the claim-FTS lane**, so live recall
misses them until some re-syncing write happens while every restart serves them. The card named the

## Decision (the card said decide, not take)

Two candidate shapes were on the table: make `replayCatchUp` report what it touched and re-sync at the
call sites (the card's first suggestion), or do the re-sync inside `replayCatchUp` when the caller passes
the lane (its second).

**Chosen: report.** Layer 1 owns no search lane and imports nothing from layer 3 today; passing a lane
*port* in would have meant either a layer-1 → layer-3 edge or a new interface that has to travel down
through exactly the same handler signatures that are already the plumbing problem. Instead the catch-up
returns `ReplayCatchUpResult { processed, touchedScopes }` and the layer that owns the lane decides what
to do about it:

- `src/layer1/replay.ts` — `replayCatchUp` collects `touchedScopes` through `processEvent` into
  `handleClaimExtracted` (the admitted claim's scope, added after `admitClaim` returns),
  `handleCorrection` (the target's scope, plus the merge target's scope on the `duplicate` branch, which
  can be a different scope) and `handleRetraction` (the claim target's scope; for an observation target,
  through `removeEvidenceFromClaims`).
- `src/layer1/corroboration.ts` — `removeEvidenceFromClaims` takes an optional `touchedScopes` out-param
  and adds the scope of every claim whose row it writes. No extra scan of the store.
- `src/layer3/search.ts` — new `resyncCatchUpScopes(searchIndex, store, touchedScopes)`: nothing when the
  lane is absent or nothing was touched.
- The five call sites pass the lane they own: `handleForget` (new optional trailing `searchIndex`),
  `handleExpireRetention` (`RetentionDeps.searchIndex`), `handleQuarantineReview` (new optional trailing
  `searchIndex`), `handleCorrect` (same), and `compiler.ts` (which re-syncs the touched scopes that stage
  4.5 does not already cover, i.e. everything except `options.scope`).
- `src/core.ts` (the four wrappers) and `src/index.ts` (the MCP `smartware_forget`,
  `smartware_quarantine_review`, `smartware_correct` tools) pass `this.searchIndex` / `searchIndex`.
  **Putting the repair in the handlers, not the wrappers, is the deliberate part**: `src/index.ts` is a
  second dispatcher surface that calls the handlers directly, so a wrapper-only fix would have left the
  MCP surface broken.

Why scoped rather than a whole-lane rebuild: the touched set is exact (collected from the writes
themselves), the cost is proportional to what the catch-up materialised, and a catch-up that replayed
nothing reports `[]` — the common single-writer case pays nothing. `SmartwareCore.open` keeps its global
re-sync; this is the same repair narrowed to the scopes that moved. The re-sync is semantics-neutral (it
makes the lane equal to whatever the store says is indexable), so it holds under either reading of the
demotion question the unmerged lanes own.

One adjacent correction: `handleQuarantineReview`'s catch-up was **not awaited**
(`replayCatchUp(evidenceDir, store, layer0, config);` as a bare statement). It is awaited now — the
re-sync must follow the replay, and un-awaited the catch-up's failures escaped the handler entirely.

## Reachability (as the card asked for, stated plainly)

A run is affected only when the catch-up meets a **claim-materialising event this process has not
replayed**:

- a `claim_extracted` L0 event written by a host or another process — OBSERVE itself rejects
  pre-extracted claims (`observe.ts:135-137`), so this is the retained replay path for legacy and
  host-written logs;
- a `correction` event written by another writer (`core.correct` in this process re-syncs the corrected
  scope itself, so the win here is a foreign or foreign-scope correction);
- another writer's tombstone/redaction that moves claim rows.

A single-writer process replays its own events at `open`, so the live window needs a multi-process or
multi-host brain — or, inside one process, an event asserting into a scope the verb's wrapper does not
re-sync (the COMPILE and CORRECT cases above, which is why they are pinned rather than dismissed as
theoretical). Production frequency is **not** measured; the probe is n=1 per configuration.
